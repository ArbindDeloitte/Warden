Auth Server A

      
Signs in users via PKCE. Issues AT_A with aud: api://banking. The frontend and Banking REST API validate these tokens. The virtual server also verifies AT_A (using A's JWKS) as the very first step before any policy check.

    

    

      
Auth Server B

      
Configured to trust Auth Server A (Trusted Servers). Accepts AT_A as a subject_token in an RFC 8693 token exchange and issues AT_B with aud: api://banking-mcp. Only the MCP virtual server ever calls Auth Server B.

    

    

      
OBO Token Cache

      
Key is sha256(AT_A) — the raw user token is never stored as a key. Backed by Redis, falls back to an in-memory Map. Proactive refresh at 80% of TTL avoids last-second expiry under load.

    

    

      
Cedar Policy Engine

      
Evaluated before every OBO exchange. Policies can match on scopes, groups, or sub. A forbid at equal or higher priority beats any permit. Default deny if no permit matches. Every decision is written to the audit log.

1

      

        
User logs in via PKCE Auth Server A

        
The React frontend redirects the user to Auth Server A (aus18gh5aw7rMbJmT698). After consent, the user gets AT_A — an access token with aud: api://banking and all banking scopes (accounts:read, payments:read …). This token is stored in sessionStorage by @okta/okta-auth-js.

      

    


    

      
2

      

        
Agent fires a proxy request mcpProxy.js

        
When the user says "Show my accounts", Agent.jsx calls mcpBanking.getAccounts() in mcpProxy.js. That calls _oktaAuth.getAccessToken() to retrieve AT_A, then posts to POST /api/proxy/<VS_ID> with Authorization: Bearer AT_A and a body of {mcp_server_id, tool_name, arguments}. The frontend never talks to the MCP server directly.

      

    


    

      
3

      

        
Virtual server verifies AT_A Auth Server A JWKS

        
The verifyToken middleware fetches jwks_uri from the virtual server's database record — set to Auth Server A's JWKS endpoint (/aus18gh5aw7rMbJmT698/v1/keys). It calls jwt.verify(AT_A, signingKey) using RS256. On success, req.tokenClaims is populated with sub, scopes, and groups.

      

    


    

      
4

      

        
Cedar policy evaluation SQLite

        
All active policies for this virtual server are loaded from SQLite. The engine evaluates each in priority order. A forbid at equal or higher priority beats any permit (deny-override). Default is deny if no permit matches. Every decision — allow or deny — is written to the audit_log table with the user's sub, scopes, tool name, and matched policy.

      

    


    

      
5

      

        
OBO token exchange Auth Server B

        
The OBO service first checks the cache with key sha256(AT_A). On a miss, it calls Auth Server B's token endpoint with RFC 8693 parameters: grant_type: token-exchange, subject_token: AT_A, audience: api://banking-mcp, and the user's banking scopes. Auth Server B trusts Auth Server A — it validates AT_A against A's JWKS and issues AT_B with the same sub (user identity preserved) but aud: api://banking-mcp. AT_B is cached at sha256(AT_A) with proactive refresh at 80% of its TTL.

      

    


    

      
6

      

        
MCP session + tool call MCP Client

        
The MCP client checks its session cache (10-min TTL). On a miss it sends an initialize JSON-RPC request to the MCP server's /mcp endpoint, receives a mcp-session-id header, then fires notifications/initialized (fire-and-forget). The actual tools/call request is sent with Authorization: Bearer AT_B and the session ID. The MCP server validates AT_B against Auth Server B's JWKS and returns the result.

      

    


    

      
7

      

        
Result returned to frontend done

        
The virtual server unpacks result.content[0].text (a JSON string), and returns the full MCP response to the frontend. mcpProxy.js JSON-parses the text and hands the data to Agent.jsx for rendering. For subsequent calls within the same session, steps 5 and 6 are fast: the OBO token is served from cache and the MCP session is reused.
