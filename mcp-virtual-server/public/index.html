A2A Policies

Control which agents may call which A2A agents through a virtual server. Rules are evaluated by priority (highest first) and the first match decides.

Deny by default. If no rule matches, the call is rejected. An Approval rule holds a matching message until an admin decides on the Approvals page; like a forbid, it also matches calls that omit the skill.

Credential Vault

Store credentials once, encrypted. Agents obtain them at runtime only when a policy allows it — nothing lives in .env files or agent code.

How agents use this

1 · Runtime checkout — the agent receives the value

Needs a permit policy with the reveal operation. The response carries a lease_id and expires_at; cache the value only until then.

curl -X POST http://localhost:3003/api/vault/checkout \
  -H "X-Agent-Token: wag_..." -H "Content-Type: application/json" \
  -d '{"secret": "stripe-key", "virtual_server_id": "<optional vs id>", "ttl_seconds": 120}'

2 · Brokered — the agent never sees the value

Needs a permit policy with the broker operation and an X-Agent-Token on the proxied call. Put vault://secret-name as the whole string of a value:

// tool arguments (resolved after policy + inbound scan, redacted from the response)
{ "api_key": "vault://stripe-key" }

// MCP server auth_config (Corridor → MCP Servers)
{ "header": "X-API-Key", "key": "vault://stripe-key" }

// Virtual server Okta client secret field
vault://okta-client-secret

For MCP server credentials, API Key Header is injected on every call; Bearer and Basic replace the Authorization header and therefore only apply when the virtual server has OBO turned off.

Brokering only happens on virtual servers that have Credential Vault switched on (Edit Virtual Server → Pipeline Features). With it off, the vault is never consulted for that virtual server.

3 · Sign — only the JWT leaves the vault

For private_key secrets; needs the sign operation. Optional metadata client_id, token_url and kid supply the default iss/sub, aud and key id.

curl -X POST http://localhost:3003/api/vault/sign \
  -H "X-Agent-Token: wag_..." -H "Content-Type: application/json" \
  -d '{"secret": "okta-private-key", "claims": {}, "expires_in": 300}'

Regex + Keyword Scanner

PII Patterns Detected

                  
    
                    
  • SSN — ###-##-####
    • 
                    
  • Credit / debit card numbers (16-digit)
    • 
                    
  • Email addresses
    • 
                    
  • US phone numbers (all formats)
    • 
                    
  • API keys — sk-, pk-, Bearer tokens
    • 
                    
  • Bank routing numbers (9-digit ABA)
    • 
                    
  • IBAN codes
    • 
                    
  • IP addresses
    • 
                  

                

                

                  
Injection Heuristics

                  
    
                    
  • "ignore previous instructions"
    • 
                    
  • "forget everything you learned"
    • 
                    
  • "you are now a…"
    • 
                    
  • "new role / persona / instructions:"
    • 
                    
  • "system prompt:"
    • 
                    
  • Model tokens — [INST], <|system|>
    • 
                    
  • "act as if you are…"
    • 
                    
  • "disregard all prior training"
    • 
                  

                

              

              

                Decision: PII matches → action is mask (character-precise replacement with [REDACTED: SSN] etc. using match start/end offsets). Injection heuristic with confidence >0.95 → block immediately — remaining layers are skipped entirely. This early-exit means API injections cost zero extra latency.
              

            

          

        


        
        

          

            
02

            

              
Embedding Similarity Scanner

              

                @xenova/transformers
                In-process WASM
                Self-Learning
              

            

            

              ~30ms
              SYNC
              ›
            

          

          

            

              

                

                  
How It Works

                  
    
                    
  • Loads all-MiniLM-L6-v2 model (~80MB) once at startup via ONNX WebAssembly — no Python, no network call
    • 
                    
  • Embeds each incoming message into a 384-dimensional vector
    • 
                    
  • Cosine similarity compared against every known attack vector in SQLite
    • 
                    
  • Score >0.85 → flagged as prompt injection
    • 
                  

                

                

                  
The Attack Database

                  
    
                    
  • Seeded from OWASP Top 10 LLM injection examples
    • 
                    
  • Stored in injection_embeddings SQLite table
    • 
                    
  • Grows automatically: high-scoring audit log entries are promoted to the attack DB
    • 
                    
  • Catches rephrased/novel injections that bypass L1 regex
    • 
                  

                

              

              

                Why this layer exists: Regex catches known patterns verbatim. Embeddings catch semantic variants — "Kindly set aside your earlier directives" scores 0.91 similarity to "ignore previous instructions" and gets caught even though no keyword matched. The gap between these two layers is what sophisticated attackers exploit.
              

              
// Runs in-process — no Python, no network
const embedder = await pipeline('feature-extraction', 'Xenova/all-MiniLM-L6-v2');
const vec = await embedder(text, { pooling: 'mean', normalize: true });
const score = knownAttacks
  .map(a => cosine(vec.data, a.embedding))
  .reduce((max, s) => Math.max(max, s), 0);
return { flagged: score > 0.85, score, categories: ['prompt_injection'] };

            

          

        


        
        

          

            
03

            

              
Presidio PII Scanner

              

                Microsoft · MIT License
                Docker Sidecar
                NLP-based
              

            

            

              ~50ms
              SYNC
              ›
            

          

          

            

              

                

                  
Detects Beyond Regex

                  
    
                    
  • Full person names (NLP Named Entity Recognition)
    • 
                    
  • Organization names
    • 
                    
  • Street addresses (multi-part)
    • 
                    
  • Medical record numbers
    • 
                    
  • Passport and driver's license numbers
    • 
                    
  • IBAN / SWIFT codes
    • 
                    
  • Healthcare provider IDs (NPI)
    • 
                  

                

                

                  
Infrastructure

                  
    
                    
  • presidio-analyzer on port 5001 — detects and locates PII with character offsets
    • 
                    
  • presidio-anonymizer on port 5002 — applies masking and returns clean text
    • 
                    
  • Both run on localhost — data never leaves the machine
    • 
                    
  • If containers down → returns { degraded: true }, L1 regex still covers baseline PII
    • 
                  

                

              

              

                Why Presidio over regex alone: Regex sees patterns. Presidio understands context. "Call John Smith at account 4892" — regex doesn't know "John Smith" is a PII entity. Presidio's spaCy NER model does. It returns exact character positions, enabling surgical masking: "Dear [REDACTED: PERSON], your balance is $500" — not a blunt full-message wipe.
              

            

          

        


        
        

          

            
04

            

              
Action Engine

              

                Decision Layer
                DB-Driven Rules
                Cedar-Style Priority
              

            

            

              <1ms
              SYNC
              ›
            

          

          

            

              

                

                  
What It Does

                  
    
                    
  • Reads interceptor_rules from SQLite (priority DESC)
    • 
                    
  • Aggregates results from all three upstream scanners
    • 
                    
  • Matches: scanner + category + score_min → action
    • 
                    
  • Makes the final, authoritative call — external services only provide data, never decisions
    • 
                    
  • Degraded scanners are skipped entirely — never block on missing evidence
    • 
                  

                

                

                  
Actions (in priority order)

                  
    
                    
  • BLOCK — returns HTTP 403 with structured reason code, proxy stops
    • 
                    
  • MASK — replaces flagged spans with [REDACTED: type] using char offsets, proxy continues with clean text
    • 
                    
  • WARN — forwards original but writes a warning entry to audit log
    • 
                    
  • LOG — records to audit log only, no action taken
    • 
                  

                

              

              

                Masking is surgical: Every scanner returns { start, end, type } for each match. Action Engine sorts matches by start position descending and replaces them in reverse order — preserving all remaining character offsets. Result: "SSN 123-45-6789 and card 4111-1111-1111-1111" → "SSN [REDACTED: SSN] and card [REDACTED: CREDIT_CARD]" without touching anything else.
              

            

          

        


        
        

          

            
05

            

              
Llama Guard 3

              

                Meta · Apache 2.0
                Ollama
                Audit Enrichment
              

            

            

              ~300ms CPU
              ASYNC
              ›
            

          

          

            

              

                

                  
Capabilities

                  
    
                    
  • Fine-tuned Llama model for safety classification across 18+ harm categories
    • 
                    
  • Runs via Ollama at localhost:11434 — zero cloud dependency
    • 
                    
  • Returns "safe" or "unsafe · S<code>" (e.g. S1=violent crimes, S5=defamation)
    • 
                    
  • CPU: ~300ms  ·  GPU: ~30ms
    • 
                    
  • Covers: violence, hate speech, sexual content, self-harm, jailbreaks, privacy
    • 
                  

                

                

                  
Why Async Only

                  
    
                    
  • 300ms CPU latency would double perceived response time if synchronous
    • 
                    
  • Results feed interceptor_log with semantic safety scores for human review
    • 
                    
  • High-severity scores surface in Audit Log for investigation
    • 
                    
  • Patterns from L5 findings tighten L1/L2 thresholds over time
    • 
                    
  • If Ollama is unreachable → silent fail, proxy is completely unaffected
    • 
                  

                

              

              

                The role it plays: Layers 1–4 block obvious violations synchronously in under 80ms. L5 catches subtle, semantic threats that regex and embeddings miss — hate speech wrapped in polite language, indirect manipulation, novel jailbreak framings. Think of it as your async analyst that builds institutional memory, not your real-time enforcer.
              

              
// Fire and forget — never awaited on the response path
llamaGuard.scan(text, direction).then(result => {
  auditLog.record({ ...result, source: 'llama-guard' });
  if (result.score > 0.9) notifyReviewQueue(result);
}).catch(() => {}); // silent fail — proxy continues unaffected

// Ollama call (inside the scanner)
const { data } = await axios.post('http://localhost:11434/api/generate', {
  model: 'llama-guard3', prompt, stream: false
});
// data.response → "safe" or "unsafe\nS1"

            

          

        

      


      
      

        
⚡ Graceful Degradation — The Core Guarantee

        
If any scanner fails — Presidio containers down, Ollama unreachable, embedding model cold — the pipeline degrades gracefully. The failed scanner returns { degraded: true }. The Action Engine skips it, logs a warning, and the proxy call continues using whatever layers did respond. Traffic never stops because a scanner is unavailable. Blocking only happens on positive evidence — absence of a scan result always resolves to allow + log, never to block.

Auth Server A

          
Signs in users via PKCE. Issues AT_A with aud: api://banking. The frontend and Banking REST API validate these tokens. The virtual server also verifies AT_A (using A's JWKS) as the very first step before any policy check.

        

        

          
Auth Server B

          
Configured to trust Auth Server A (Trusted Servers). Accepts AT_A as a subject_token in an RFC 8693 token exchange and issues AT_B with aud: api://banking-mcp. Only the MCP virtual server ever calls Auth Server B.

        

        

          
OBO Token Cache

          
Key is sha256(AT_A) — the raw user token is never stored as a key. Backed by Redis, falls back to an in-memory Map. Proactive refresh at 80% of TTL avoids last-second expiry under load.

        

        

          
Cedar Policy Engine

          
Evaluated before every OBO exchange. Policies can match on scopes, groups, or sub. A forbid at equal or higher priority beats any permit. Default deny if no permit matches. Every decision is written to the audit log.

User logs in via PKCE Auth Server A

            
The React frontend redirects the user to Auth Server A. After consent, the user gets AT_A — an access token with aud: api://banking and all banking scopes (accounts:read, payments:read …). This token is stored in sessionStorage by @okta/okta-auth-js.

          

        


        

          
2

          

            
Agent fires a proxy request mcpProxy.js

            
When the user says "Show my accounts", Agent.jsx calls mcpBanking.getAccounts() in mcpProxy.js. That retrieves AT_A and posts to POST /api/proxy/<VS_ID> with Authorization: Bearer AT_A and a body of {mcp_server_id, tool_name, arguments}. The frontend never talks to the MCP server directly.

          

        


        

          
3

          

            
Virtual server verifies AT_A Auth Server A JWKS

            
The verifyToken middleware fetches jwks_uri from the virtual server's database record — set to Auth Server A's JWKS endpoint. It calls jwt.verify(AT_A, signingKey) using RS256. On success, req.tokenClaims is populated with sub, scopes, and groups.

          

        


        

          
4

          

            
Cedar policy evaluation SQLite

            
All active policies for this virtual server are loaded from SQLite. The engine evaluates each in priority order. A forbid at equal or higher priority beats any permit (deny-override). Default is deny if no permit matches. Every decision is written to the audit_log table with the user's sub, scopes, tool name, and matched policy.

          

        


        

          
5

          

            
OBO token exchange Auth Server B

            
The OBO service first checks the cache with key sha256(AT_A). On a miss, it calls Auth Server B with RFC 8693 parameters: grant_type: token-exchange, subject_token: AT_A, audience: api://banking-mcp. Auth Server B validates AT_A against A's JWKS and issues AT_B with the same sub but aud: api://banking-mcp. AT_B is cached with proactive refresh at 80% of its TTL.

          

        


        

          
6

          

            
MCP session + tool call MCP Client

            
The MCP client checks its session cache (10-min TTL). On a miss it sends an initialize JSON-RPC request to the MCP server's /mcp endpoint, receives a mcp-session-id header, then fires notifications/initialized. The actual tools/call request is sent with Authorization: Bearer AT_B and the session ID. The MCP server validates AT_B against Auth Server B's JWKS and returns the result.

          

        


        

          
7

          

            
Result returned to frontend done

            
The virtual server unpacks result.content[0].text (a JSON string) and returns the full MCP response to the frontend. For subsequent calls within the same session, steps 5 and 6 are fast: the OBO token is served from cache and the MCP session is reused — no Okta round-trip needed.

Identity Model

          
Warden operates a two-layer identity framework: every request carries a user identity (Okta JWT, proving who the human is) and an optional agent identity (wag_* token, proving which software is acting on their behalf). Both layers are independently verified, logged, and policy-evaluated.

Overview

          
The Two Identity Layers

          
Traditional API gateways authenticate the caller. Warden authenticates two callers simultaneously — the human and the agent acting on their behalf — using different token types, different trust boundaries, and different enforcement mechanisms.

          

            

              
👤

Configuration

          
Three Levels of Agent Enforcement

          
Agent identity enforcement is configured per Virtual Server. Start with observability-only and tighten as needed — no data is lost when changing modes.

Log Only

              
Agent token is read and resolved if present. Identity is recorded in the event log. Calls without a token pass through normally. Ideal for rollout — gain visibility before adding gates.

Security Design

          
Security Properties

          
The identity model is built to be safe by design — tokens are never stored in recoverable form, and every trust decision is explicit.

          

            

              
🔒

              
Tokens stored as SHA-256 only

              
The raw wag_* token is shown exactly once (at registration or rotation) and never persisted. The database stores only the SHA-256 hash. A compromised DB reveals no usable tokens.

            

            

              
⛔

              
Disabled agents are hard-blocked

              
Disabling an agent in the Agent Hub immediately invalidates all calls. The token hash lookup runs before any policy check — a disabled agent's call returns 403 regardless of VS settings or allowlist membership.

            

            

              
🧩

              
Orthogonal to API keys

              
API keys answer "is this caller authorized to use Warden?" Agent tokens answer "which named agent is making this specific call?" They're independent — both can coexist, and agent identity works whether API key enforcement is on or off.

            

            

              
📋

              
Every call fully attributed

              
The event log records user_sub (human), agent_name (software), tool called, VS, decision, and matched policy on every proxy call. Both identities survive the OBO exchange and appear together in audit.

            

            

              
🚫

              
Agent never touches user credentials

              
The OBO token exchange is performed by Warden on behalf of the user. The agent only holds its own wag_* token and the user's AT_A. AT_B (the MCP-scoped token) is exchanged and forwarded by the gateway, never by the agent.

            

            

              
🔄

              
Token rotation without downtime

              
Rotating a token via the Agent Hub generates a new wag_* token and immediately invalidates the previous hash. The new token is shown once and must be updated in the agent's environment. No restart of Warden is required.

Rule Evaluation Flow

          
How a single rule moves an agent from registration to group membership.

          

            
          

        


        
        

          
When Does Sync Happen?

          
Rules are evaluated automatically — no manual triggers needed.

          

            

              
1

              

                
Agent registered

                
When a new agent is created via the Agent Hub, all group rules are evaluated against its metadata immediately in the background. Matching groups receive the agent as a member with source=rule.

              

            

            

              
2

              

                
Agent metadata updated

                
Editing an agent's metadata triggers re-evaluation across all groups. Memberships are added or removed based on whether rules still match — manual members are never touched.

              

            

            

              
3

              

                
Rule created or changed

                
Saving a rule (create, update, delete) immediately re-syncs that specific group — evaluating all agents against the new rule set and reconciling membership.

              

            

            

              
4

              

                
Manual sync

                
The "Sync" button on the Group Rules page triggers a full re-evaluation of all agents against all rules for every group at once — useful after bulk agent imports.

Match Modes

          
Each rule has one match mode that controls how multiple conditions combine.

          

            

              
ALL

              
ALL — Logical AND

              
Every condition in the rule must pass for the agent to be assigned. Use ALL when you need agents that simultaneously meet every criterion — tighter, more specific rules.

Split complex logic into multiple focused rules so each one is easy to read and audit.
          

        


      

    


    
    

    

      

        
        
A2A · Overview

        
A2A Gateway

        
How Warden lets agents call other agents over the Agent2Agent (A2A) protocol — with caller identity, deny-by-default policy, content scanning, and an audit trail on every call.

        
What it doesArchitectureRequest lifecycleBuilding blocksTrust modelNot supported

      


      


        

          
What it does

          
A2A is an open protocol (current version 1.0.0) that lets one agent send a task to another over JSON-RPC 2.0 on HTTP(S). Warden acts as the gateway between them, the same way it already does for MCP tool calls.

          

            
🛡️
Gateway, not a host

              
Warden never runs an agent. Remote agents run elsewhere; you register each one by its Agent Card and assign it to a virtual server. Warden sits between the caller and the target.

            
🔌
A2A 1.0 and 0.3, JSON-RPC only

              
Implements the JSON-RPC binding of A2A 1.0 and A2A 0.3. Each registered agent speaks one version, chosen at registration (or auto-detected from its card), and its gateway speaks that same version to callers and to the agent, with no translation. Earlier versions are rejected. The REST and gRPC bindings are not implemented.

            
🏠
Self-contained

              
The A2A path needs no external services: no Redis, no OBO token exchange and no message queue. It runs on Warden's own libraries and its SQLite database. Okta is contacted only to verify an optional user token, and enabled interceptors use Warden's local scanners.

          

        


        

          
Architecture

          
Every A2A call goes caller → Warden → target. Warden never trusts the caller's claims about the target, and the target never has to trust the caller directly.

Building blocks

          
What you configure in the Warden UI, and what each piece does.

          

            
📡 Virtual server protocol

              
Each virtual server is MCP (default), A2A or Both. Only A2A/Both servers expose /a2a/… and accept A2A agent assignments. An MCP-only server rejects them.

            
🤝 A2A Agents registry

              
Remote agents registered by Agent Card URL (fetched by Warden, 8 s timeout) or pasted card JSON. The card is cached; if a refresh fails, the cached card stays in use and the error is recorded.

            
🪪 Gateway Agent Card

              
Warden serves its own copy of each card at /a2a/{vs}/{agent}/.well-known/agent-card.json. Its only interface is Warden's endpoint; signatures, securitySchemes and securityRequirements are removed because the card was modified.

            
🧑‍💻 Caller identity

              
Callers are ordinary Warden Agent Hub agents authenticating with X-Agent-Token (wag_…). Their Agent Groups can be used in policies, so membership rules also drive A2A access.

            
🛂 A2A Policies

              
Deny-by-default rules per virtual server: caller (any / agent / group) → target (any / agent) → skills, with permit, forbid or approval and a priority. Highest priority first; the first match decides. An approval rule holds the message in the Approvals queue until an admin decides.

            
🔐 Outbound credentials

              
Optional per remote agent: bearer token, API-key header or basic auth, encrypted at rest (AES-256-GCM). The API never returns the secret.

            
🧾 Tasks

              
Tasks returned by a target are stored under the calling agent. Another agent asking for the same task ID gets TaskNotFound.

            
📊 Audit & scoring

              
Calls that reach the policy stage, and failed authentications, are logged as a2a_call events (Event Log → A2A Calls). Allow/deny decisions feed the calling agent's risk score, as do outbound interceptor findings.

          

        


        

          
Trust model: the delegation token

          
Warden never forwards the caller's credentials. It signs a short-lived token of its own, and the target verifies it offline.

          

            Warden generates an Ed25519 key pair on first use and stores it in SQLite. For each forwarded call it mints a JWT (alg: EdDSA) valid for 60 seconds, sent in the X-Warden-Delegation header. The public key is published at GET /.well-known/jwks.json. A target fetches the JWKS once, caches it, and verifies signature, iss and exp without calling Warden again.

Why it matters: a target that rejects calls without a valid Warden token can't be reached by bypassing the gateway. The demo Credit Card Agent does exactly this — calling it directly returns 401.

          
Loop and depth limits are best effort. They only work when agents pass Warden's token along on their own onward calls (in X-Warden-Delegation). An agent that omits it starts a fresh chain, so this is a safeguard against accidents, not a security boundary.

Optional: let the card agent see the user's identity

            
The chat and Python agent send the user's Okta access token as X-User-Token. Warden forwards the user's identity to the card agent only if it can verify that token. To enable it:

    •

    • 
                
  • Leave Client ID, Client Secret, OBO Audience / Scope and JWKS URI blank, and leave OBO Token Exchange and Advanced — Connect with an IDP unchecked (the latter only appears when Interceptors is ticked) — A2A uses none of them.

JSON-RPC methods

          
Names below are the A2A 1.0 PascalCase methods. For an agent registered as A2A 0.3 the equivalents are message/send, message/stream, tasks/get, tasks/cancel and tasks/resubscribe, with the same checks (0.3 has no ListTasks; push config is tasks/pushNotificationConfig/* and the extended card agent/getAuthenticatedExtendedCard, both unsupported as below). A method from the other version gets -32601 with a hint naming the right one. Warden forwards the supported ones and answers the rest itself.

          

            

              
MethodBehavior in Warden

              
                
SendMessageRequires params.message with a parts array (else -32602). The skill is read from params.metadata.skillId or params.message.metadata.skillId. Returns whatever the target returns (a Task or a Message). A returned Task is stored under the caller. If message.taskId is set, the caller must own that task.

                
SendStreamingMessageSame checks as SendMessage; the target's text/event-stream is relayed. Each event is a JSON-RPC response whose id is the caller's request ID; text is scanned per event and task state is updated. Warden adds a : keep-alive comment every 15 s. The 60 s timeout covers connecting and receiving headers only, so long streams are not cut off. Errors after the stream starts are sent as an event.

                
GetTaskRequires params.id and ownership. Forwarded to the target. If the target is unreachable, the cached task is returned with metadata["warden.stale"] = true.

                
ListTasksLocal only. Returns up to 100 of the caller's tasks for this virtual server and target, most recently updated first, as {tasks, nextPageToken: "", pageSize, totalSize}. Filter and paging parameters are ignored. These response field names follow A2A conventions but were not checked against the proto.

                
CancelTaskRequires params.id and ownership; forwarded to the target.

                
SubscribeToTaskRequires params.id and ownership; the target's event stream is relayed like SendStreamingMessage.

                
Create / Get / List / DeleteTaskPushNotificationConfigNot supported: -32003.

                
GetExtendedAgentCardNot configured: -32007.

                
anything else-32601 Method not found.

Using the official A2A SDKs

          
Warden's gateway has been exercised with a client and agents built on the official JavaScript SDK (@a2a-js/sdk 1.3.0) and Python SDK (a2a-sdk 1.3.0), JSON-RPC binding. These are the practical points.

          

            

              
TopicWhat to know

              
                
Base URL needs a trailing slashThe SDK clients look for .well-known/agent-card.json relative to the URL you give them. Pass http://warden/a2a/{vs}/{agent}/ (with the trailing slash), or pass the full card URL with an empty path. Without the slash they request …/a2a/{vs}/.well-known/…, which is not an agent card.

                
AuthenticationSend the agent token as Authorization: Bearer (what stock clients' auth hooks set) or X-Agent-Token. Warden's gateway card does not advertise a security scheme, so configure the token on the client yourself.

                
Declaring a skillA2A has no standard way to name a skill on a request. Warden reads params.metadata.skillId (the SDK's metadata field on the request). A skill-scoped forbid also matches a call that names no skill, so a generic client that sets none is blocked by such a rule.

                
Gateway card capabilitiesThe gateway card always reports pushNotifications: false and extendedAgentCard: false and omits the target's extensions, because Warden does not serve or forward those, even if the target advertises them.

                
Error pass-throughErrors the target itself returns (for example TASK_NOT_CANCELABLE, -32002) are relayed as-is, including their data details.

Evaluation rules
            
    
              
  • Active policies for the virtual server are checked in priority order; the first match decides. A match on a forbid denies; a match on a permit allows.
    • 
              
  • If nothing matches, the call is denied (deny by default). With no policies at all, every A2A call is denied.
    • 
              
  • A skill-restricted permit does not match a request that names no skill.
    • 
              
  • A skill-restricted forbid does match a request that names no skill, so leaving the skill out can't bypass it.
    • 
              
  • An approval match holds the call: the gateway answers HTTP 202 with JSON-RPC error -32011 (data: ticket_id, poll_url, expires_at, timeout_action) and does not contact the target. An admin approves or denies it on the Approvals page; once approved Warden forwards the message and the caller polls /api/approvals/{id}/status for the result. A skill-restricted approval also matches a request that names no skill. Streaming requests run as a normal request once approved. Follow-ups on a task the caller already owns (GetTask, CancelTask …) are allowed without a new approval.
    • 
              
  • Follow-up methods (GetTask, CancelTask, SubscribeToTask, ListTasks) cannot name a skill, so: a skill-restricted permit still applies (the caller may continue work it was allowed to start), while a skill-restricted forbid is skipped (otherwise it would block every follow-up call from everyone). They still need a matching caller/target permit, and task ownership still limits who can touch a task.
    •

Applies when the matched permit policy has Require verified user token checked.

How "invalid" is decided: Warden classifies the verification error by its message. Text mentioning jwt, signature, malformed, expired, invalid token, audience or issuer counts as an invalid token; anything else (network errors, timeouts, key lookup failures, no JWKS configured) counts as infrastructure. This is a heuristic — a wrong key ID is classed as infrastructure, which is why fail open means "user identity is optional". Verification times out after 8 s.

        


        

          
Outbound credentials

          
What Warden presents to a remote agent, set per A2A agent on the registry page (Credential) or at registration.

          

            

              
TypeSecret formatSent as

              
                
none—Authorization: Bearer <delegation JWT>

                
bearerTokenAuthorization: Bearer <secret>

                
headerValue, plus a header name matching [A-Za-z0-9-]{1,64}<header>: <secret>

                
basicusername:password (a colon is required)Authorization: Basic base64(secret)

              
            

          

          

            
    
              
  • Encrypted at rest with AES-256-GCM. The key is WARDEN_SECRETS_KEY if set; otherwise an auto-generated file .warden-secrets.key in the same folder as the database, so a leaked copy of the database alone does not expose stored credentials. Keep that file out of version control (mcp-virtual-server/.gitignore already lists the default path).
    • 
              
  • Never returned by the API — only auth_type, auth_header and has_secret.
    • 
              
  • Reserved header names can't be used: host, content-length, content-type, accept, a2a-version, x-warden-delegation, transfer-encoding, connection.
    • 
              
  • Redirects are refused on forwarded calls so a credential is never sent to a different host.
    • 
              
  • If a stored secret can't be decrypted (for example, the key was lost), the call fails and does not count toward the circuit breaker. The caller sees HTTP 502 "Target agent unreachable" with the real cause in error.data.reason, and GetTask falls back to its cached task. The secret must be re-entered.
    • 
              
  • There is no key-rotation feature: changing the key makes existing stored secrets unreadable.
    •

Audit & scoring

          
One a2a_call event per request that gets past request validation (streams add a second event when they complete).

          

            Level is info (allowed), warn (task not found, or an error the target itself returned and Warden passed through), block (denied, blocked, loop, or failed authentication) or error (target failure). Event data includes: caller (agent_id, agent_name), target (target_agent_id, target_name), method, decision (allow / deny / block / error / auth_failed), reason, policy_id, skill, user_status, user_degraded, task_id, task_state and chain_depth. Failed authentications are logged with no caller identity.
Not logged: invalid JSON-RPC requests, unknown routes, unsupported A2A-Version, unsupported methods, missing-parameter errors (-32602), task-ID conflicts, and non-JSON HTTP errors from the target.
          

          

            Scoring. Only events whose decision is allow or deny count toward an agent's or virtual server's risk score, so target outages and failed logins never change a score. Interceptor findings on A2A traffic are attributed to the calling agent. By default scoring counts only outbound findings (the "only outbound" setting), so a blocked inbound message is not scored unless that setting is turned off. As with MCP, the virtual server must have Interceptors enabled for its calls to be scored. The Score History page lists only MCP proxy calls and interceptor scans; A2A decisions affect the score but do not appear there.
