01

            

              
Regex + Keyword Scanner

              

                In-process Node.js
                Always On
                Zero Cost
              

            

            

              <1ms
              SYNC
              ›
            

          

          

            

              

                

                  
PII Patterns Detected

                  
    
                    
  • SSN — ###-##-####
    • 
                    
  • Credit / debit card numbers (16-digit)
    • 
                    
  • Email addresses
    • 
                    
  • US phone numbers (all formats)
    • 
                    
  • API keys — sk-, pk-, Bearer tokens
    • 
                    
  • Bank routing numbers (9-digit ABA)
    • 
                    
  • IBAN codes
    • 
                    
  • IP addresses
    • 
                  

                

                

                  
Injection Heuristics

                  
    
                    
  • "ignore previous instructions"
    • 
                    
  • "forget everything you learned"
    • 
                    
  • "you are now a…"
    • 
                    
  • "new role / persona / instructions:"
    • 
                    
  • "system prompt:"
    • 
                    
  • Model tokens — [INST], <|system|>
    • 
                    
  • "act as if you are…"
    • 
                    
  • "disregard all prior training"
    • 
                  

                

              

              

                Decision: PII matches → action is mask (character-precise replacement with [REDACTED: SSN] etc. using match start/end offsets). Injection heuristic with confidence >0.95 → block immediately — remaining layers are skipped entirely. This early-exit means API injections cost zero extra latency.
              

            

          

        


        
        

          

            
02

            

              
Embedding Similarity Scanner

              

                @xenova/transformers
                In-process WASM
                Self-Learning
              

            

            

              ~30ms
              SYNC
              ›
            

          

          

            

              

                

                  
How It Works

                  
    
                    
  • Loads all-MiniLM-L6-v2 model (~80MB) once at startup via ONNX WebAssembly — no Python, no network call
    • 
                    
  • Embeds each incoming message into a 384-dimensional vector
    • 
                    
  • Cosine similarity compared against every known attack vector in SQLite
    • 
                    
  • Score >0.85 → flagged as prompt injection
    • 
                  

                

                

                  
The Attack Database

                  
    
                    
  • Seeded from OWASP Top 10 LLM injection examples
    • 
                    
  • Stored in injection_embeddings SQLite table
    • 
                    
  • Grows automatically: high-scoring audit log entries are promoted to the attack DB
    • 
                    
  • Catches rephrased/novel injections that bypass L1 regex
    • 
                  

                

              

              

                Why this layer exists: Regex catches known patterns verbatim. Embeddings catch semantic variants — "Kindly set aside your earlier directives" scores 0.91 similarity to "ignore previous instructions" and gets caught even though no keyword matched. The gap between these two layers is what sophisticated attackers exploit.
              

              
// Runs in-process — no Python, no network
const embedder = await pipeline('feature-extraction', 'Xenova/all-MiniLM-L6-v2');
const vec = await embedder(text, { pooling: 'mean', normalize: true });
const score = knownAttacks
  .map(a => cosine(vec.data, a.embedding))
  .reduce((max, s) => Math.max(max, s), 0);
return { flagged: score > 0.85, score, categories: ['prompt_injection'] };

            

          

        


        
        

          

            
03

            

              
Presidio PII Scanner

              

                Microsoft · MIT License
                Docker Sidecar
                NLP-based
              

            

            

              ~50ms
              SYNC
              ›
            

          

          

            

              

                

                  
Detects Beyond Regex

                  
    
                    
  • Full person names (NLP Named Entity Recognition)
    • 
                    
  • Organization names
    • 
                    
  • Street addresses (multi-part)
    • 
                    
  • Medical record numbers
    • 
                    
  • Passport and driver's license numbers
    • 
                    
  • IBAN / SWIFT codes
    • 
                    
  • Healthcare provider IDs (NPI)
    • 
                  

                

                

                  
Infrastructure

                  
    
                    
  • presidio-analyzer on port 5001 — detects and locates PII with character offsets
    • 
                    
  • presidio-anonymizer on port 5002 — applies masking and returns clean text
    • 
                    
  • Both run on localhost — data never leaves the machine
    • 
                    
  • If containers down → returns { degraded: true }, L1 regex still covers baseline PII
    • 
                  

                

              

              

                Why Presidio over regex alone: Regex sees patterns. Presidio understands context. "Call John Smith at account 4892" — regex doesn't know "John Smith" is a PII entity. Presidio's spaCy NER model does. It returns exact character positions, enabling surgical masking: "Dear [REDACTED: PERSON], your balance is $500" — not a blunt full-message wipe.
              

            

          

        


        
        

          

            
04

            

              
Action Engine

              

                Decision Layer
                DB-Driven Rules
                Cedar-Style Priority
              

            

            

              <1ms
              SYNC
              ›
            

          

          

            

              

                

                  
What It Does

                  
    
                    
  • Reads interceptor_rules from SQLite (priority DESC)
    • 
                    
  • Aggregates results from all three upstream scanners
    • 
                    
  • Matches: scanner + category + score_min → action
    • 
                    
  • Makes the final, authoritative call — external services only provide data, never decisions
    • 
                    
  • Degraded scanners are skipped entirely — never block on missing evidence
    • 
                  

                

                

                  
Actions (in priority order)

                  
    
                    
  • BLOCK — returns HTTP 403 with structured reason code, proxy stops
    • 
                    
  • MASK — replaces flagged spans with [REDACTED: type] using char offsets, proxy continues with clean text
    • 
                    
  • WARN — forwards original but writes a warning entry to audit log
    • 
                    
  • LOG — records to audit log only, no action taken
    • 
                  

                

              

              

                Masking is surgical: Every scanner returns { start, end, type } for each match. Action Engine sorts matches by start position descending and replaces them in reverse order — preserving all remaining character offsets. Result: "SSN 123-45-6789 and card 4111-1111-1111-1111" → "SSN [REDACTED: SSN] and card [REDACTED: CREDIT_CARD]" without touching anything else.
              

            

          

        


        
        

          

            
05

            

              
Llama Guard 3

              

                Meta · Apache 2.0
                Ollama
                Audit Enrichment
              

            

            

              ~300ms CPU
              ASYNC
              ›
            

          

          

            

              

                

                  
Capabilities

                  
    
                    
  • Fine-tuned Llama model for safety classification across 18+ harm categories
    • 
                    
  • Runs via Ollama at localhost:11434 — zero cloud dependency
    • 
                    
  • Returns "safe" or "unsafe · S<code>" (e.g. S1=violent crimes, S5=defamation)
    • 
                    
  • CPU: ~300ms  ·  GPU: ~30ms
    • 
                    
  • Covers: violence, hate speech, sexual content, self-harm, jailbreaks, privacy
    • 
                  

                

                

                  
Why Async Only

                  
    
                    
  • 300ms CPU latency would double perceived response time if synchronous
    • 
                    
  • Results feed interceptor_log with semantic safety scores for human review
    • 
                    
  • High-severity scores surface in Audit Log for investigation
    • 
                    
  • Patterns from L5 findings tighten L1/L2 thresholds over time
    • 
                    
  • If Ollama is unreachable → silent fail, proxy is completely unaffected
    • 
                  

                

              

              

                The role it plays: Layers 1–4 block obvious violations synchronously in under 80ms. L5 catches subtle, semantic threats that regex and embeddings miss — hate speech wrapped in polite language, indirect manipulation, novel jailbreak framings. Think of it as your async analyst that builds institutional memory, not your real-time enforcer.
              

              
// Fire and forget — never awaited on the response path
llamaGuard.scan(text, direction).then(result => {
  auditLog.record({ ...result, source: 'llama-guard' });
  if (result.score > 0.9) notifyReviewQueue(result);
}).catch(() => {}); // silent fail — proxy continues unaffected

// Ollama call (inside the scanner)
const { data } = await axios.post('http://localhost:11434/api/generate', {
  model: 'llama-guard3', prompt, stream: false
});
// data.response → "safe" or "unsafe\nS1"

            

          

        

      


      
      

        
⚡ Graceful Degradation — The Core Guarantee

        
If any scanner fails — Presidio containers down, Ollama unreachable, embedding model cold — the pipeline degrades gracefully. The failed scanner returns { degraded: true }. The Action Engine skips it, logs a warning, and the proxy call continues using whatever layers did respond. Traffic never stops because a scanner is unavailable. Blocking only happens on positive evidence — absence of a scan result always resolves to allow + log, never to block.

Auth Server A

          
Signs in users via PKCE. Issues AT_A with aud: api://banking. The frontend and Banking REST API validate these tokens. The virtual server also verifies AT_A (using A's JWKS) as the very first step before any policy check.

        

        

          
Auth Server B

          
Configured to trust Auth Server A (Trusted Servers). Accepts AT_A as a subject_token in an RFC 8693 token exchange and issues AT_B with aud: api://banking-mcp. Only the MCP virtual server ever calls Auth Server B.

        

        

          
OBO Token Cache

          
Key is sha256(AT_A) — the raw user token is never stored as a key. Backed by Redis, falls back to an in-memory Map. Proactive refresh at 80% of TTL avoids last-second expiry under load.

        

        

          
Cedar Policy Engine

          
Evaluated before every OBO exchange. Policies can match on scopes, groups, or sub. A forbid at equal or higher priority beats any permit. Default deny if no permit matches. Every decision is written to the audit log.

1

          

            
User logs in via PKCE Auth Server A

            
The React frontend redirects the user to Auth Server A. After consent, the user gets AT_A — an access token with aud: api://banking and all banking scopes (accounts:read, payments:read …). This token is stored in sessionStorage by @okta/okta-auth-js.

          

        


        

          
2

          

            
Agent fires a proxy request mcpProxy.js

            
When the user says "Show my accounts", Agent.jsx calls mcpBanking.getAccounts() in mcpProxy.js. That retrieves AT_A and posts to POST /api/proxy/<VS_ID> with Authorization: Bearer AT_A and a body of {mcp_server_id, tool_name, arguments}. The frontend never talks to the MCP server directly.

          

        


        

          
3

          

            
Virtual server verifies AT_A Auth Server A JWKS

            
The verifyToken middleware fetches jwks_uri from the virtual server's database record — set to Auth Server A's JWKS endpoint. It calls jwt.verify(AT_A, signingKey) using RS256. On success, req.tokenClaims is populated with sub, scopes, and groups.

          

        


        

          
4

          

            
Cedar policy evaluation SQLite

            
All active policies for this virtual server are loaded from SQLite. The engine evaluates each in priority order. A forbid at equal or higher priority beats any permit (deny-override). Default is deny if no permit matches. Every decision is written to the audit_log table with the user's sub, scopes, tool name, and matched policy.

          

        


        

          
5

          

            
OBO token exchange Auth Server B

            
The OBO service first checks the cache with key sha256(AT_A). On a miss, it calls Auth Server B with RFC 8693 parameters: grant_type: token-exchange, subject_token: AT_A, audience: api://banking-mcp. Auth Server B validates AT_A against A's JWKS and issues AT_B with the same sub but aud: api://banking-mcp. AT_B is cached with proactive refresh at 80% of its TTL.

          

        


        

          
6

          

            
MCP session + tool call MCP Client

            
The MCP client checks its session cache (10-min TTL). On a miss it sends an initialize JSON-RPC request to the MCP server's /mcp endpoint, receives a mcp-session-id header, then fires notifications/initialized. The actual tools/call request is sent with Authorization: Bearer AT_B and the session ID. The MCP server validates AT_B against Auth Server B's JWKS and returns the result.

          

        


        

          
7

          

            
Result returned to frontend done

            
The virtual server unpacks result.content[0].text (a JSON string) and returns the full MCP response to the frontend. For subsequent calls within the same session, steps 5 and 6 are fast: the OBO token is served from cache and the MCP session is reused — no Okta round-trip needed.

Pipeline Features

    

      

        
        

          
🛡 Interceptors

          
Run inbound and outbound scanner pipeline (Regex + Presidio PII detection, masking, blocking). When disabled, tool arguments and responses pass through unscanned.

        

      

      

        
        

          
🔒 Token Policy Evaluation

          
Evaluate Cedar-style permit/forbid/approval policies and OBO token scopes. When disabled, all tool calls are auto-allowed (audit logging and OBO exchange still run).
