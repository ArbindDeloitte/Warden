TENANT-OBO-IDJAG-ONBOARDING-2026-10-01

PointGuardAI MCP Gateway — onboarding OBO and ID-JAG for your tenant

What we need from you, what we configure, and how you test it. Version 2026-10-01. The console walkthrough (§3.5) and the tests (§4) were run end to end for both OBO and ID-JAG on that date. Added 2026-10-05: §7, an Okta example for OBO. It follows Okta's published steps and our gateway code; it has not yet been run end to end against an Okta org in this revision.

1. What this gives you

Your AI agents call tools through the PointGuardAI MCP Gateway. With OBO or ID-JAG configured, the gateway calls the downstream service as the signed-in user: never as a shared service account, and the agent never holds a credential for that service.

The gateway decides on two identities on every call:

Identity How it arrives How it is checked
The human a token from your identity provider, sent in the x-user-token header signature, issuer and audience verified against your IdP's published keys
The agent its name, sent in the X-Agent-Token header matched against the agents you declare and the rules you approve

You choose one of two mechanisms per downstream service:

OBO (RFC 8693 token exchange) ID-JAG (Cross App Access: RFC 8693, then RFC 7523)
Hops 1 2
Who issues the final token your IdP's authorization server the downstream service's own authorization server
Token the user presents an access token an ID token
Use it when the downstream service trusts tokens from your IdP the downstream service runs its own authorization server and supports Cross App Access

2. What you need to provide

Send client secrets through your secure channel, never in email or a ticket. The gateway stores them encrypted at rest and never returns them. Every API and console view shows *****.

2.1 Always: your identity provider (the human side)

# Item Example We use it to

2 Discovery URL (/.well-known/openid-configuration) or the JWKS URL …/v1/keys verify token signatures

Using Okta? §7 shows where each of these items is set in the Okta Admin Console.

2.4 If the service uses ID-JAG

★ Check this first: ID-JAG works only if both your IdP supports Cross App Access (XAA) and the downstream service accepts identity assertions at its own authorization server. If the service does not support XAA, use OBO or delegated consent instead. No gateway configuration can work around that.

# Item Notes
17 Hop A token endpoint: your IdP's endpoint that issues the identity assertion in Okta this is the org authorization server (https://<org>.okta.com/oauth2/v1/token), not a custom one
18 A requesting app for the gateway: client ID grants authorization_code + refresh_token, offline_access allowed, your redirect URI
19 Client authentication for that app: private_key_jwt (Okta requires it) or client secret for private_key_jwt, we generate the key pair and give you the public JWK to register; you send us the key ID (kid) you registered it under
20 The resource app with Cross App Access enabled its issuer URL (becomes the assertion's audience) and its audience
21 The XAA connection from the requesting app to the resource app resource indicator = the downstream MCP server URL (#7); scopes (#9)
22 Hop B token endpoint: the downstream service's authorization server where the assertion is redeemed for an access token
23 Hop B client, if that server requires client authentication: client ID + secret some servers issue a separate client per resource connection. Send the resource-side one, not the requesting one

2.5 Your agents and your rules

# Item Notes
24 The agents that will call through the gateway, with a name for each we register each one; any undeclared name is refused
25 Which agent may call which tools, for which groups e.g. readers may list but never delete; only the writer agent may create
26 Whether each agent gets its own endpoint recommended: one virtual server per agent, so an agent reaching another agent's endpoint is itself a finding

3. What we configure

This section shows every setting and where it comes from, so you can review it. Most of it is entered in the MCP Gateway console (§3.5) by your admin or by us. A few settings are not in the console yet; PointGuardAI applies those for you.

3.1 Trust in your IdP (gateway deployment, items 1–5)

Set once per tenant gateway and applied when the gateway is redeployed:

Setting From
OBO_USER_TOKEN_ISSUER #1
OBO_USER_TOKEN_JWKS_URL #2
OBO_USER_TOKEN_AUDIENCE #3
OBO_USER_TOKEN_GROUPS_CLAIM #4 (default groups)
OBO_USER_TOKEN_CLIENT_CLAIM #5

⚠ One audience per gateway. If you run OBO and ID-JAG side by side, the two user tokens carry different audiences, so the audience check has to be relaxed for that gateway. Signature and issuer are still verified. A per-provider audience is planned.

3.2 Each downstream service (items 7–23)

  1. Register the MCP server with the one-time token (#11) so the gateway discovers its tools. A server registered directly for OBO or ID-JAG discovers nothing, because there is no user at registration time.
  2. Switch it to the exchange configuration below. The tools stay.
  3. Create the virtual servers and attach the tools (#26).

OBO, stored as the MCP server's OAuth configuration:

}

3.3 Agents and rules (items 24–26)

We register the agents, write the rules, and confirm the policy engine is enforcing (a deny stops the call) rather than observing.

In the MCP Gateway console (§3.5), or from us:

Virtual server URL(s) <gateway>/servers/<id>/mcp, one per agent if #26

Step 5: write the rules

Extensions → Policies → Access Rules → New rule. Each rule has a name, an effect (Deny, Allow or Require approval), an optional virtual server, and conditions that must all hold. Write one rule per line of #25. Rules that make the negative tests in §4.4 pass:

Rule name Effect Virtual server Condition
No human, no action Deny Any server User token present · is false
Refuse undeclared agents Deny Any server Agent · is not one of · your agent names (#24)
Readers may not create Deny the writer's server Tool · is one of · the create tool, and User groups · includes any of · mcp-readers
One agent per endpoint Deny e.g. crm-reader-agent Agent · is not one of · crm-reader-agent

The Check a request panel on the same page runs the same engine as the gateway: pick a virtual server and tool, type an agent, user and groups, and it shows the verdict before any agent calls.

Step 6: tell us you are done

We then apply the settings from the table at the end of step 3 and the IdP trust from §3.1, confirm enforcement is on, and you test (§4).

4. How you test it

4.1 What you need

  • The values from §3.4.

  • A fresh user token for a test user (#6), obtained by a normal sign-in through your app (authorization code with PKCE):

    • OBO: the user's access token, with the audience from #3.
    • ID-JAG: the user's ID token. ID tokens are short-lived, so get a fresh one just before testing.

    ⚠ Password-grant shortcuts (ROPC) are usually blocked by IdP sign-on policies. Use a real sign-in.

export GW="https://<your-gateway>"
export VS="<virtual-server-id>"
export GW_TOKEN="<gateway API token>"
export USER_TOKEN="<access token (OBO) or ID token (ID-JAG)>"
export AGENT="<declared agent name>"
export TOOL="<tool name>"

4.2 Step 1: the gateway answers and lists the tools

curl -s -X POST "$GW/servers/$VS/mcp" \
  -H "Authorization: Bearer $GW_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

Expect the tool names from §3.4.

4.3 Step 2: the call succeeds as the user

curl -s -X POST "$GW/servers/$VS/mcp" \
  -H "Authorization: Bearer $GW_TOKEN" \
  -H "x-user-token: Bearer $USER_TOKEN" \
  -H "X-Agent-Token: $AGENT" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d "{\"jsonrpc\":\"2.0\",\"id\":2,\"method\":\"tools/call\",
       \"params\":{\"name\":\"$TOOL\",\"arguments\":{}}}"

★ x-user-token must carry the word Bearer followed by the token. A bare token is refused.

Expect real data with "isError": false. ⚠ A response can be HTTP 200 and "isError": true. That is a failure; read the message.

Confirm on the downstream service that the action was recorded against the test user, not a service account. This is the proof that the delegation worked.

4.4 Step 3: the negative tests (these are the point)

A refusal comes back as HTTP 200 with "isError": true and a message that says why. With the rules from §3.5 step 5:

# Change Expect in the message
N1 remove the x-user-token header PDP_DENY … Denyed by rule 'No human, no action'
N2 send an expired or tampered user token USER_TOKEN_INVALID … X-User-Token verification failed
N3 send the reader user on a write tool PDP_DENY … Denyed by rule 'Readers may not create'
N4 send an undeclared agent name PDP_DENY … Denyed by rule 'Refuse undeclared agents'
N5 (#26) send an agent to another agent's virtual server PDP_DENY … Denyed by rule 'One agent per endpoint'
N6 a user who is valid in your IdP but unknown to the downstream service an error from the downstream service (proves the user's identity, not ours, reached it)

4.5 Step 4: the evidence

Every call leaves one trace. Ask us for it, or view it in the platform console:

Line Means
PDP: ALLOW | subject=<your user> the policy decided on the human
Successfully performed RFC 8693 token exchange Hop A (OBO's only hop)
Successfully redeemed ID-JAG assertion at resource AS (RFC 7523) Hop B (ID-JAG only)
PDP_DENY … with the rule name a negative test refused for the right reason

The trace records which token was sent upstream. It never contains a token or a secret.

6. What to know before you start

  1. Agent identity is declared, not yet cryptographically verified. The gateway admits only the agent names you declare and enforces rules on them. Verified agent credentials, issued by your IdP or by the PointGuardAI control plane, are on the roadmap.
  2. Configuration is partly self-service. The MCP server, virtual servers, rules and API tokens are in the console (§3.5). Trust in your IdP (§3.1) and the settings listed at the end of step 3 are applied by PointGuardAI. A tenant-facing Identity Providers page with a "test this token" check is planned.
  3. ID-JAG depends on your vendors. Both your IdP and the downstream service must support Cross App Access. Many SaaS services do not yet.
  4. One gateway per tenant. Your configuration is not shared with any other customer.

7. Example: Okta as your OBO authorization server

This section shows what to set up in Okta so the gateway can exchange your user's token for a downstream token (OBO, §2.3). It covers OBO only. Values in braces are placeholders: {yourOktaDomain}, {authServerId}, and so on.

7.1 Before you start

  • ★ Licensing. Okta's documentation says on-behalf-of token exchange requests are accepted only if your org bought or renewed an NHI Authentication Token subscription on or after 14 August 2026. Check this with your Okta account team first. Without it, no configuration below works.
  • A custom authorization server. Okta documents OBO token exchange on custom authorization servers: the one named default, or one you create. Use one of those, not the org authorization server (/oauth2/v1/token).
  • An Okta admin who can create app integrations and edit authorization servers.
  • The downstream MCP server (#7) accepts access tokens from this authorization server and maps the token's sub to its own user (#10).

The example uses one authorization server. Both the user's token and the exchanged token come from it. §7.3 step 7 covers the case where the downstream service trusts a different authorization server in the same Okta org.

7.2 What you create

# In Okta Purpose Feeds item
A A custom authorization server issues the user's token and performs the exchange #1, #2, #3, #12, #14
B Custom scopes on that server what the exchanged token is allowed to do #9
C A groups claim on that server lets rules decide on the user's groups #4
D The user-facing app (OIDC) your users sign in to it; it obtains the user's access token the token in x-user-token
E An API Services app for the gateway, with the Token Exchange grant the client the gateway authenticates as when it exchanges #13
F Two access policies, each with a rule admit D for the sign-in and E for the exchange #16

7.3 Step by step in the Okta Admin Console

Step 1: the authorization server (A)

Security → API → Authorization Servers → Add Authorization Server. Enter a Name, an Audience and a Description, then save.

  • Audience: a URI that names your MCP APIs, for example api://mcp. Okta puts it in the aud claim of every access token this server issues. You will send it as #3 and #14.
  • Note the server's Issuer (https://{yourOktaDomain}/oauth2/{authServerId}) and its Metadata URI (https://{yourOktaDomain}/oauth2/{authServerId}/.well-known/openid-configuration).

You can use the existing default server instead. Its {authServerId} is default. A new org's default server may have no access policy; step 6 adds one.

Step 2: custom scopes (B)

On the same server, open Scopes → Add Scope. Create one scope per kind of access the agents need, for example mcp:read and mcp:write (#9).

⚠ Do not plan on offline_access or the OpenID Connect scopes (openid, profile, email) for the exchanged token. Okta does not allow them when a service app performs the exchange.

Step 3: the groups claim (C)

On the same server, open Claims → Add Claim:

Field Value
Name groups (the gateway reads groups unless told otherwise, #4)
Include in token type Access Token
Value type Groups
Filter Matches regex .*, or a narrower filter that returns only the groups your rules use, for example mcp-.*

Okta access tokens do not carry groups unless you add this claim. Without it, rules on User groups (§3.5 step 5) never match.

Step 4: the user-facing app (D)

Applications → Applications → Create App Integration → OIDC - OpenID Connect, then Native Application (or Single-Page Application / Web Application, matching how your users actually sign in). Use Authorization Code with PKCE. Assign it to the users or groups who will use the agents, including both test users (#6).

This app is not given to the gateway. It only produces the user's access token, which your agent sends in x-user-token (§4.1).

Step 5: the gateway's exchange client (E)

Applications → Applications → Create App Integration → API Services → Next. Name it, for example PointGuardAI MCP Gateway, and save. Then:

  1. General → General Settings → Edit.
  2. In Grant type, click Advanced and select Token Exchange. Save. (On Okta Classic Engine, Token Exchange is listed directly under Grant type.)
  3. Leave Client authentication on Client secret.
  4. Copy the Client ID and the Client secret. These are #13. Send the secret through your secure channel (§2).

★ Create this as an API Services app. In our testing, enabling Token Exchange on an ordinary OIDC web app produced a different Okta flow that demanded an actor_token the gateway does not send.

Step 6: access policies and rules (F)

On the authorization server, open Access Policies → Add New Access Policy. Create two policies:

Policy Assign to: The following clients Rule (Add Rule)
Users to MCP the user-facing app (D) IF Grant type is: Authorization Code · AND User is: Any user assigned to the app · AND Scopes requested: the scopes the sign-in asks for (at least openid)
Gateway exchange the gateway app (E) IF Grant type is: click Advanced, select Token Exchange · AND User is: Any user assigned to the app, or the groups that may use the agents · AND Scopes requested: the scopes from step 2

Save each rule with Create rule.

⚠ Okta's OBO guide shows these policies with the scope condition only. We list the grant type and user conditions too, because the rule dialog offers them; confirm they are set as above when you save.

Step 7 (optional): the downstream service trusts a second authorization server

If the downstream service validates tokens from a different custom authorization server in the same Okta org:

  1. Open that second server: Security → API → edit it → Trusted servers → Add Server, find the server from step 1, Add, Done.
  2. Add steps 2 and 6 (Gateway exchange only) on the second server.
  3. Then #12 is the second server's token endpoint and #14 is the second server's audience. #1–#3 stay those of the first server, because that is where the user's token comes from.

7.4 Values to send us, and where each one goes

Every value below is read by the PointGuardAI MCP Gateway. Your agents need only the user's access token from app D (sent in x-user-token) and the gateway values from §3.4. The PointGuardAI control plane reads nothing from Okta for OBO.

Item Okta value Gateway setting
#1 Issuer: https://{yourOktaDomain}/oauth2/{authServerId} OBO_USER_TOKEN_ISSUER, and Issuer URL in the console (§3.5 step 3)
#2 https://{yourOktaDomain}/oauth2/{authServerId}/v1/keys (the jwks_uri in the Metadata URI) OBO_USER_TOKEN_JWKS_URL
#3 the server's Audience, e.g. api://mcp OBO_USER_TOKEN_AUDIENCE
#4 groups (step 3) OBO_USER_TOKEN_GROUPS_CLAIM
#5 cid (Okta's client claim) OBO_USER_TOKEN_CLIENT_CLAIM. ★ Set it: the gateway's default is client_id, which Okta does not use
#9 the scopes from step 2, e.g. mcp:read mcp:write MCP server OAuth configuration scopes
#12 https://{yourOktaDomain}/oauth2/{authServerId}/v1/token token_url, Token URL in the console
#13 Client ID and secret of app E client_id, client_secret, Client ID / Client Secret in the console
#14 the server's Audience (or the second server's, step 7) audience
#15 Client secret the gateway sends the client ID and secret in the request body (client_secret_post) for the exchange

The gateway sends Okta exactly these form fields on each exchange: grant_type=urn:ietf:params:oauth:grant-type:token-exchange, subject_token (the user's access token), subject_token_type and requested_token_type (both urn:ietf:params:oauth:token-type:access_token, the default when the console fields are left empty), client_id, client_secret, audience and scope. These match Okta's OBO request.

For attribution the gateway reads email, falling back to sub, from the user's token. Okta access tokens carry the user's login in sub, so no extra claim is needed.

7.5 Check Okta before you call the gateway

Run the exchange yourself, the same way the gateway will. Use a fresh access token for a test user from app D.

export OKTA_TOKEN_URL="https://{yourOktaDomain}/oauth2/{authServerId}/v1/token"
export GW_CLIENT_ID="{gatewayAppClientId}"
export GW_CLIENT_SECRET="{gatewayAppClientSecret}"
export USER_TOKEN="{user access token from app D}"

curl -s -X POST "$OKTA_TOKEN_URL" \
  -H "Accept: application/json" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
  --data-urlencode "subject_token_type=urn:ietf:params:oauth:token-type:access_token" \
  --data-urlencode "requested_token_type=urn:ietf:params:oauth:token-type:access_token" \
  --data-urlencode "subject_token=$USER_TOKEN" \
  --data-urlencode "client_id=$GW_CLIENT_ID" \
  --data-urlencode "client_secret=$GW_CLIENT_SECRET" \
  --data-urlencode "audience=api://mcp" \
  --data-urlencode "scope=mcp:read mcp:write"

Expect HTTP 200 with:

{
  "token_type": "Bearer",
  "expires_in": 3600,
  "access_token": "eyJ…",
  "scope": "mcp:read mcp:write",
  "issued_token_type": "urn:ietf:params:oauth:token-type:access_token"
}

Decode the new access_token (its payload only) and check:

Claim Must be
iss https://{yourOktaDomain}/oauth2/{authServerId}
aud your audience (#14)
sub the test user, not the gateway app
cid the gateway app's client ID (E)
scp the scopes you asked for

Also decode the user's token and check iss (#1), aud (#3), cid (app D) and groups (step 3). Then run the tests in §4.

7.6 When the Okta side fails

Through the gateway, a refused exchange appears as identity provider rejected the exchange with the HTTP status only. The curl in §7.5 shows Okta's own error and error_description, so start there. The codes below are the standard OAuth ones; Okta's description text varies.

Okta error Likely cause Fix
